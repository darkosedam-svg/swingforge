# WU-2C — tournament + excursion + report (branch `wu/2c`)

Built: `lab/tournament.py` (config matrix, anchored walk-forward, the sweep, results rows), `lab/excursion.py` (MAE/MFE, `HoldBars`, raw-signal control), `lab/report.py` (markdown report); 105 tests in `test_tournament.py`/`test_excursion.py`/`test_report.py` plus the shared `tests/unit/synth_store.py` and the `tests/unit/snapshots/report_small.md` snapshot. Coverage: tournament 100%, excursion 100%, report 99% (one partial branch, a comprehension exit). Full suite 542 passed (`-m "not slow"` 524 in ~30 s, `-m slow` 18 in ~45 s); `ruff`, `mypy swingforge`, `lint-imports` clean.

**What the CLI must supply.** `EntryFactory.__call__(name: str, instrument: Instrument, *, baseline_rate: float | None, seed: int) -> Strategy` and `SessionFactory.__call__(mode: str, profile: str) -> Callable[[Bar], bool]` (`profile` is `instrument.session_profile`). ⚠ `baseline_rate` is **trades per 1,000 4H bars**, not a per-bar probability, and is `None` for every entry but `baseline`; the tournament runs all of an instrument's `ict` configs first, averages their rate, and falls back to `1.0` when ICT produced nothing. ⚠ `seed` is `crc32(config.id) ^ run seed`, derived per config so it does not move when the matrix is narrowed or reordered — **`Baseline` (and any other entry drawing random numbers) must seed itself from this argument and nothing else.** Exits come from `EXIT_GRID` by name (`EXIT_RULES`/`exit_rule`); rules are stateless, so one instance serves every config.

**One replay per config, not one per split.** The walk-forward is anchored and nothing is fitted on IS (the exit grid is enumerated, not optimised), so one replay over `[warmup_start(start), end)` yields exactly the trades every split would: a trade is in split *k*'s IS iff `entry_fill.ts < is_end_k`, in its OOS iff `oos_start_k <= ts < oos_end_k`. 2,016 × 12 replays become 2,016. Warmup is `ceil(60 × 7/5) = 84` calendar days so a five-session FX week still seeds 60 Daily bars; **no entry is taken before `start`** because `run_config` wraps the session predicate with `bar.ts_open >= start`. ⚠ Each instrument's window is the **intersection** of the requested `start`/`end` with its own 4H range (`max(start, first)`, `min(end, last + 4h)`), so a 4-year request against a 6-month listing is excluded as `insufficient_history:6` rather than handed empty early splits.

**Two-pass V, `n_trials`, and the IS-selected view.** Pass 1 replays every config and keeps only what pass 2 reads — a `_Replayed` (trades, `n_bars`, `resolution_mode`) per config and **one close series per instrument**, not one per config (that copy was the memory blow-up). Pass 2 computes `trial_sr_variance = var(ddof=1)` of `gate.sharpe(pooled OOS R)` over every config with ≥ 2 trades — the enumerated matrix only, not the derived views — and evaluates each gate with ⚠ **`n_trials = len(matrix) + len(IS-selected views)`**: a view is a trial of the same search (it picks among 16 exits per split) and is the candidate a reader is most likely to trade, so deflating by the matrix alone under-deflates it. Both figures are on `TournamentResult` (`n_trials`, `trial_sr_variance`). A view is built per `(entry, session, instrument)`: per split the exit with the highest IS expectancy (ties to `EXIT_GRID` order, split skipped below 10 IS trades), its OOS trades pooled across splits under `entry|IS_SELECTED|session|venue:symbol`, its `n_is` pooled over each split's *incremental* IS window so no trade is counted twice; `TournamentResult.selection` maps that id to `{split label: exit}`. ⚠ A `baseline` config is its own rule-4 baseline and so fails rule 4 by construction — correct, not a bug.

**Results rows and the error policy.** Exactly `store._RESULTS_COLUMNS`. One row per split (`split = "%Y-%m"` of `oos_start`, gate columns `None`) plus one `split="pooled"` row carrying the gate; every row of a run shares the run's own `ts`. ⚠ `mar`/`mar_bh`/`dsr_prob`/`boot_p5`/`diff_p5` are mapped for storage: `inf -> ±1e9` (`_INF_SENTINEL`), `nan -> None`; the report reads `TournamentResult.gates` instead, so it still prints a true `∞`. Pooled `n_is`/`exp_is` use the **last** split's IS window (anchored, so it contains every earlier one). Trades and equity go to `f"{run_id}:{config.id}"`; `run_tournament` calls `store.upsert_instruments(instruments)` first because `write_trades` resolves instruments through that table. Every catch site logs with `logger.exception`. A config that will not *run* becomes one pooled row with `excluded_reason="error:<Type>: <msg>"[:200]` and leaves the gate — and ⚠ **`MAX_CONSECUTIVE_ERRORS = 20` failures in a row abort the whole run** with `RuntimeError(...) from` the first of them (the counter resets on the first config that runs, so scattered failures never trip it). A config that ran but could not be *stored* keeps everything — trades, place in V, gate verdict — and is only annotated `persist_error:<Type>: <msg>` on its pooled row, joined onto the gate's own reason if there is one. A blown-up `gate.evaluate` is still a row, with no gate columns.

**`keep_runs` and `resume`.** `TournamentResult.runs` is empty unless `run_tournament(..., keep_runs=True)`: nothing downstream needs it (the report reads `rows`, `gates`, `oos_trades`) and 2,016 `ConfigRun`s do not fit. `resume=True` skips any config whose child run id already has stored trades, reading them back and recomputing `n_bars`/`resolution_mode` from the source bars — a re-run of an interrupted sweep then costs one query per config instead of a replay. ⚠ Caveats: writes are upsert-idempotent per key but only as a **superset** (a re-run producing *fewer* trades leaves the earlier extras behind, so `resume` is safe only against the same code, data and window under the same `run_id`); a config that legitimately produced **zero** trades looks unfinished and is replayed every time; and `keep_runs` + `resume` reads each equity curve back, which a plain resume does not.

**Report.** ⚠ The gate, excursion and cost-stress tables are **truncated**: every config that passed, the top `top_n` by `exp_oos`, every `IS_SELECTED` row, and a line counting the rest — a config with no `exp_oos` at all never appears (its row would be all en dashes, and the `Excluded` section names it with its reason). The header says the `results` table, not the markdown, is what anything downstream should read. The report **escapes `|` in every table cell** — config ids are `entry|exit|session|venue:symbol`, so without it the gate table renders as ragged nonsense. `excursion_summary` and the stressed expectancy are computed once per shown config, not once per table.

**Timing, measured on a 4-year synthetic store** (8,766 4H + 1,461 Daily bars, one instrument): `run_config` is **0.87 s** at 136 trades and **1.71 s** at 310 trades, while `store.write_trades` + `write_equity` for the same config cost **5.1 s** and **8.6 s** — 5–6× the replay. So 2,016 configs ≈ **30–57 min of replay** but ≈ **3.3–5.8 h wall clock**, dominated by the store. ⚠ **`Store.write_trades` is the bottleneck (~30 ms per trade), and it is fixable in WU-1E, not here.** Two causes, both measured: (1) it calls `_instrument_by_venue_symbol` **once per trade** — 8.1 ms each — while `Store.trades` caches that lookup per distinct `(venue, symbol)`; caching it in `write_trades` too is a three-line fix. (2) `context_snapshot` falls into `_bulk_upsert`'s object-dtype bucket, ~20 ms/row even when every snapshot is `b""`. Both are amplified because **DuckDB retries a failed `import pandas` roughly 14 times per statement** (44,618 `nt.stat` calls for one 455-trade write); adding `pandas` to the dependencies, or typing `context_snapshot` into a bucket, removes most of it. Measures taken here, both internal and both tested to change nothing: `_WarmContext` (passed via `Engine(context=...)`) reads ATR/ADX on 4H and Daily after every push so `Context`'s memo stays on its O(1) step instead of re-running Wilder's recurrence at each sparse read — **3.4×** on a 20-month replay, an identical `ConfigRun` (`test_warm_context_does_not_change_the_run`); the real fix belongs in `Context`, which owns the memo. `_MemoisedSource` reads each instrument's merged stream once instead of once per config, which is also what makes the per-instrument closes and a resumed config's bar count free. Small decisions: `run_config` gained `baseline_rate`, `seed`, `warm_context` and `exit_override` (the last is how `excursion.raw_signal_excursion`, which also takes `seed`, swaps in `HoldBars` without touching the config id); `TournamentResult` gained `oos_trades` so the report's excursion and cost-stress sections read the same pooled OOS trades the gate did. `ConfigRun.resolution_mode` is computed from the bars (`"subbars"` iff every in-range 4H bar carries sub-bars, `"mixed"` if some, `"pessimistic"` if none), not from the resolver, which reports per call. `buy_and_hold_curve` chains OOS segments multiplicatively so the IS gaps are neither credited nor charged, and always starts at `1.0` so `gate.mar` can always read it. Not done: nothing reads WU-1D's advice to check lag-1..5 autocorrelation and drop the bootstrap to `p=1.0` — the gate's `p=0.1` is used as shipped.
